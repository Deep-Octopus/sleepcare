# 阶段二 P2-05 真实授权与数据生命周期

> 执行日期：2026-08-19
>
> 覆盖需求：正式同意准备状态、真实能力关闭门禁、固定测试数据生命周期请求台账
>
> 数据边界：仅使用固定测试记录，不包含真实个人数据或医疗内容
>
> 任务结果：通用契约与关闭优先门禁完成；真实数据、正式同意、身份核验和任何数据处置继续保持关闭

## 1. 范围与非范围

### 1.1 本任务范围

- 增加数据治理准备接口，逐项展示服务告知、隐私、通知和智能处理四类正式同意的版本与评审状态。
- 展示身份核验、同意证据、撤回、最小必要字段、保存、更正、删除、导出、敏感访问审计和备份恢复十项治理评审门禁。
- 新增固定测试用户的数据生命周期请求台账，支持查阅副本、更正、限制处理和删除四类请求事实。
- 所有请求固定为待政策确认，保存策略配置摘要、记录来源、操作人和部门归属。
- 增加显式 `DISABLED|CONTRACT_TEST` 配置、GORM 迁移、督导按钮、Casbin 权限、Swagger 契约和用户详情治理面板。
- 保持幂等、乐观锁、DataScope、机构范围和固定测试记录门禁。

### 1.2 本任务非范围

- 不启用真实用户、真实个人数据、正式同意记录或正式试用。
- 不编写服务告知、隐私、通知或智能处理同意正文，不保存身份材料或同意证据。
- 不确定保存天数、归档方式、删除范围、匿名化方法、导出格式、水印、审批或交付方式。
- 不执行查阅副本、更正、限制处理、删除或匿名化，也不提供相关状态转换和批量入口。
- 不新增合规、审计或机构管理员角色，不改变既有角色含义。
- 不启用真实短信、医疗内容或面向用户的 AI，不在单任务内执行页面点触。
- 不提前实现 P2-06 工作人员影子验证、P2-07 灰度演练或 P2-08 集中验收。

## 2. 歧义处理与安全决策

R2 要求阶段二验证用户授权、撤回、身份验证和数据制度，同时明确这些正式输入必须由业务、合规和安全责任人确认。当前仓库没有可审计的正式正文、身份核验方案、保存期限、删除/匿名化规则、导出审批或真实试用授权。直接补全上述内容会改变数据模型、责任边界和合规结论，因此本任务暂停向真实处置延伸，并冻结为以下范围：

- “任务完成”指通用接口、关闭态、权限和测试证据完成，不表示真实能力已经获批；
- 正式能力开关始终返回关闭，不能通过配置改成生产模式；
- 显式测试模式只允许追加待政策请求，不允许执行请求；
- 不把 P1-02 的测试参与记录改造成正式同意，也不迁移、覆盖或删除既有记录；
- 后续获得正式输入后，必须重新冻结同意证据、身份核验、生命周期状态、执行责任、审计和迁移，再单独实现。

## 3. 数据模型与迁移

新增 `care_data_lifecycle_requests` 表：

| 字段 | 用途 |
| --- | --- |
| `organization_id` | 请求发生时的机构 |
| `care_client_id` | 固定测试康养用户 |
| `request_type` | `ACCESS_COPY|CORRECTION|RESTRICTION|ERASURE` |
| `status` | 固定为 `PENDING_POLICY` |
| `requested_at` | 请求事实发生时间 |
| `source` | 固定为 `STAFF_RECORDED` |
| `reason` | 工作人员记录的请求事实说明，最长 1000 字符 |
| `identity_verification_status` | 固定为 `NOT_CONFIGURED` |
| `governance_mode` | 记录时的治理模式快照 |
| `policy_snapshot_digest` | 非敏感治理配置的 SHA-256 摘要，不对外返回 |
| `execution_allowed` | 固定为 `false` |
| `synthetic` | 固定测试记录标志 |
| `dept_id`、`created_by` | 由统一 DataScope 回调盖章 |

表通过现有 GORM AutoMigrate 增量创建，不修改 `care_clients`、`consent_records` 或服务过程表。回退代码不会自动删表；物理清理需要独立审批、备份和迁移方案。

## 4. 状态、版本与幂等

当前状态只有：

```text
PENDING_POLICY
```

不存在“已验证”“处理中”“已完成”“已拒绝”或“已删除”等转换，因为身份核验、执行主体、时限和处置规则尚未批准。每条记录均返回 `identityVerificationStatus=NOT_CONFIGURED` 和 `executionAllowed=false`。

写请求要求：

1. 当前用户是授权机构的督导；
2. 目标是可见的固定测试康养用户；
3. `expectedVersion` 与当前用户版本一致；
4. 提供非空 `Idempotency-Key`、合法请求类型、请求时间、固定来源和事实说明；
5. `CONTRACT_TEST` 与固定测试数据门禁同时开启。

成功后只追加请求并增加用户版本。相同键与相同请求重放原结果，即使之后关闭门禁仍保持重放稳定；相同键与不同请求冲突，旧版本请求失败。

## 5. 配置与准备状态

`care.data-governance.mode` 只接受：

- `DISABLED`：默认值，不允许记录请求；
- `CONTRACT_TEST`：必须同时开启固定测试数据门禁，只允许追加待政策请求。

任何其他模式都会阻止启动。配置只包含四个非敏感版本号和十四个评审布尔值，不包含正文、证件、保存期限、审批凭据、密钥或外部地址。

准备接口始终返回：

- `usageScope=TEST_ONLY`
- `realDataEnabled=false`
- `formalConsentEnabled=false`
- `lifecycleExecutionEnabled=false`

`requestRecordingEnabled` 只反映测试请求记录门禁，不能被前端解释为正式能力已启用。稳定阻塞码用于指出真实数据、正式同意、执行能力以及各评审项仍未开放。

## 6. 接口与权限

| 方法 | 路径 | 权限与用途 |
| --- | --- | --- |
| `GET` | `/care/data-governance-readiness` | 督导读取关闭状态、四类同意准备项和治理评审项 |
| `GET` | `/care/clients/{id}/data-lifecycle-requests` | 督导分页读取授权范围内固定测试用户请求，可按类型过滤 |
| `POST` | `/care/clients/{id}/data-lifecycle-requests` | 督导在显式测试门禁下追加待政策请求 |

员工私有路由继续使用 `JWT -> MustChangePwdGuard -> Casbin -> DataScope`。Service 层透传 Context，并校验业务角色、机构范围和目标记录类型。`recordLifecycleRequest` 按钮在用户列表页和隐藏详情页只授予督导；页面按钮不能替代后端授权。

普通管理员、管家、医护、内容管理员、跨机构身份、非测试记录和缺失业务身份均失败关闭。当前没有面向康养用户受限会话的数据生命周期接口。

## 7. 前端行为

督导打开康养用户详情时可看到治理面板。面板只展示：

- 真实数据、正式同意和数据处置均未启用；
- 四类同意内容的版本与评审状态；
- 十项治理规则的评审状态；
- 当前用户的待政策请求台账。

只有测试请求记录门禁开启时才显示“记录请求”按钮。一次对话生成并稳定复用同一幂等键；成功后刷新用户版本与台账。界面不提供执行、编辑、删除、导出或批量操作，也不会把请求显示为已完成处置。

页面样式使用 UnoCSS 原子类和既有 Element Plus 组件，没有新增内联样式或 scoped CSS。
