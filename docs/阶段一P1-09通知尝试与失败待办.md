# 阶段一 P1-09 通知尝试与失败待办

## 范围

- 建立通知请求、独立 attempt 与标准回执的持久事实。
- 用无网络测试 adapter 覆盖待提交、已提交通道、已受理、已送达、失败和未知。
- 为失败/未知创建统一送达异常待办；同一逻辑请求只保留一个活动待办。
- 支持责任管家对失败/未知 attempt 补发，保留旧 attempt 并创建带来源的新 attempt。
- 支持责任管家或医护对任务追加人工联系事实。
- 提供通知记录页面、回执时间线、状态筛选和补发入口。
- 落地场景 B：客户 `20002`、计划 `23002`、D1–D5 `24101`–`24105`、失败 attempt `28101` 和未知补发 `28102`。

## 非范围

- 不接正式短信、供应商 SDK、手机号、通知正文、模板、签名、回执验签或限流。
- 不启用面向用户的 AI，不编写医疗内容，不修改问卷、答案、规则或事项处理结论。
- 不实现任务逾期待办、设备自动接入或阶段二通知运营能力。
- 不把打开、同意、开始或提交当作通知送达回执。
- 不完成 P1-10 的全角色终局菜单矩阵，也不做页面点触；集中验收归 P1-11。

## 数据模型

### `notification_requests`

每个任务一个稳定通知意图，保存任务、客户、通道、请求时间、固定测试门禁和标准归属字段。

### `notification_attempts`

以 `notificationRequestId + attemptNo` 唯一。每次尝试保存：

- 任务、客户、`retryOfAttemptId` 和 `DEMO` 通道；
- 独立状态与请求、提交、受理、送达、终结时间；
- 失败码、补发原因和乐观锁版本；
- 操作者、操作名、幂等键摘要和请求摘要。

补发从不更新旧 attempt。

### `notification_delivery_events`

以 attempt 和事件键去重，只追加 `fromStatus`、`toStatus`、事件类型、发生时间、失败码及 adapter 引用摘要。原始 adapter 引用不对外返回。

### 任务联系与待办

- 联系记录复用 `CarePathEvent`，新增 `channel` 字段并写 `TaskContactRecorded`；任务只增加版本，执行状态不变。
- 失败/未知复用 `TodoItem` 的 `DELIVERY_ISSUE`，来源键使用逻辑通知请求，避免重试重复建活动待办。

## 状态

```text
PENDING -> SUBMITTED_TO_PROVIDER -> ACCEPTED -> DELIVERED
                                         \---> FAILED
                                         \---> UNKNOWN
```

- `ACCEPTED` 不设置 `deliveredAt`，页面明确显示尚未确认送达。
- `DELIVERED|FAILED|UNKNOWN` 是单次 attempt 终态；不同事件键不能继续改写。
- 同一回执事件键重放返回原结果，不重复写事件或待办。
- 只有 `FAILED|UNKNOWN` 允许补发；新 attempt 从 `PENDING` 重新开始。
- 送达异常与任务的执行、时效、复核状态完全独立。

## 接口

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/care/deliveries` | 分页查询授权范围 attempt 和回执证据 |
| POST | `/care/deliveries/{id}/resend` | 为失败/未知终态创建新 attempt |
| POST | `/care/tasks/{id}/contact-records` | 追加任务人工联系事实 |

列表保持 `{ page, pageSize, total, list }`，所有响应保持 `{ code, data, msg }`。两个写接口都要求 `Idempotency-Key` 与 `expectedVersion`。

冻结契约原先要求补发携带 attempt 版本，却未在列表模型返回版本；本任务以向后兼容方式为 `NotificationAttempt` 增加 `version`，同时补充事件证据、提交时间、客户显示信息和补发来源。

## 权限

- 管家、医护和上级可按 DataScope 与责任/管理范围读取通知记录。
- 补发只允许该客户当前责任管家。
- 联系记录允许当前责任管家或当前责任医护。
- 跨部门、同部门但无当前分配、错误角色、缺少业务身份的请求全部失败关闭。
- Casbin、按钮和菜单只作为外层权限，Service 仍执行责任关系与版本校验。

## 迁移与初始化

- AutoMigrate 登记三张通知表，并为 `care_path_events` 增加联系渠道字段。
- 初始化幂等登记通知记录菜单、补发按钮、任务联系按钮、三条 API 元数据和角色策略。
- 场景 B 初始化两条保留旧事实的 attempts，并验证 D1 为 `OPEN`、D2–D5 为 `SCHEDULED`。
- 测试 adapter 不访问网络，初始化与应用运行时都不会发送短信。

## 关键测试与证据

- adapter 固定输出 `SUBMITTED_TO_PROVIDER -> ACCEPTED -> 终态`，受理与送达字段保持分离。
- 终态保护返回 `41601`，非法状态顺序返回 `41602`。
- 失败和第二次未知只形成一个活动待办；重复终态回执不重复写入。
- 补发创建新 attempt、保留旧失败记录；相同幂等请求重放，不同参数冲突，旧版本冲突。
- 管家责任范围、医护只读、上级管理范围和同部门非责任人拒绝均有服务测试。
- 人工联系追加结构化任务事件和 outbox，任务执行状态不变，版本增加。
- 初始化两次后 ID、attempt 数、待办数及 D1–D5 状态保持不变。
- 定向 Go 测试已覆盖 notification、carepath、API、路由和初始化包；全后端只编译通过。
- 前端定向 ESLint 与生产构建通过；Swagger 重建一致，静态 OpenAPI 的 39 条路径、116 个 schema 和 406 个引用均可解析。
- 页面点触按阶段规则留到 P1-11。
