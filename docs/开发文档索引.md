## 当前建议决策

- 首期采用模块化单体，不立即拆微服务。
- 业务使用普通 GVA package；只有独立安装/交付诉求才考虑 plugin。
- 阶段一是在可持续架构上完成的首个 OSA 纵向闭环，验收使用贴近真实业务的合成数据，不建设一次性实现。
- 主动咨询、满意度和正式通知进入阶段二；失眠/CBT-I、设备自动接入和 AI 进入阶段三。三个阶段均属于长期交付范围，按子项分批验收。
- 康养用户端采用独立移动布局和受限会话，不套用员工后台账号/菜单模型。
- 通知、设备、AI 和呼叫平台使用 port + adapter，核心业务状态机留在本系统。
- GVA MCP 仅作为受控开发工具；`gva_analyze` 与 `gva_execute` 均需人工确认和可回退基线。

## 启用真实能力前必须关闭的门禁

1. 正式 D1–D5 内容、填写角色及医疗规则获得授权确认；
2. 实际组织、责任关系及敏感数据访问范围确认；
3. 真实用户身份、授权、撤回、保留及安全制度确认；
4. 正式短信供应商、资质、回执和运行保障验证完成；
5. AI 对外或临床相关能力完成知识审核、数据政策和人工兜底验证。

通用工程开发不等待上述外部输入。自管 Git、Compose 环境、代码生成模板和 DataScope 漂移由项目组作为内部工程任务自行关闭。
