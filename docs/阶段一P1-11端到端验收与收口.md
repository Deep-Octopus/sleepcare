## 1. 范围与非范围

本任务对已实现的阶段一能力做集中收口：从全新 Compose 数据卷启动，使用固定业务时钟运行客户端、管家、医护和上级四个隔离会话，验证提交、关注事项、处置、复核、汇总、通知异常和越权拒绝。

本任务不新增业务页面、生产接口或数据表，不接入真实短信、设备、用户侧 AI、正式问卷/规则或真实个人数据，也不提前开始阶段二。

## 2. 数据模型、状态、接口与权限

- 数据模型：没有新表、新列或新枚举；验收复用已有的客户、责任关系、计划、任务、答卷、关注事项、待办、指导和通知记录。
- 主流程状态：客户任务由 `OPEN` 经 `IN_PROGRESS` 到 `SUBMITTED`；关注事项由 `PENDING_ACK` 经确认、联系、升级、复核和结果记录到 `CLOSED`。
- 通知失败分支：首次 attempt 为 `FAILED`，补发 attempt 为 `UNKNOWN`，D1 仍为 `OPEN`，D2～D5 仍为 `SCHEDULED`。
- 生产接口：无新增或破坏性变更；验收按已冻结的 OpenAPI 和 Swagger 调用。
- 权限：员工端继续经过 JWT、强制改密保护、Casbin、DataScope 和业务责任关系；客户端仅能使用限定 Path 的 HttpOnly Cookie 访问本人任务。
- 跨机构负向样例使用真实后端路由验证，返回 HTTP `403` 和业务码 `41104`。

## 3. 迁移、重置与固定时钟

- P1-11 的可重复验收通过显式 RFC3339 值启用 `care.fixture-now`；日常 Compose 默认把 `GVA_CARE_FIXTURE_NOW` 设为空并使用系统时间。
- 显式空环境值会覆盖已有服务配置卷中残留的固定时间，因此从验收环境切回日常运行不需要重置卷或业务数据。
- 配置在启动时校验 RFC3339，非法时间会使服务失败关闭。
- 全新环境仅重置本项目的 MySQL、Redis、服务配置、上传和日志卷；`make up` 在初始化系统库后重启 server，保证业务迁移和初始记录在第一次干净启动就生效。
- 再次执行 `make up` 不重复创建记录，也不改写已完成的业务流程。

## 6. 验收过程中修复的收口缺陷

1. 干净库首次启动时 server 早于系统表初始化，业务迁移未执行；`make up` 现在会在初始化后重启 server。
2. 场景 B 首次通知失败中途中止可留下半成品 attempt；整个初始化场景现在由外层事务保护，责任关系时间窗与固定时钟对齐。
3. 固定业务时钟早于操作系统时钟时，Cookie 过期时间会立即失效；现在按业务时钟计算剩余时长，再映射到 HTTP 时钟。
4. 实时汇总会排除与当前毫秒相同的新事实；今日预览截止点现在包含当前持久化毫秒。
