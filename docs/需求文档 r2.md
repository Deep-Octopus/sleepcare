- Should：尽量交付，时间不足时可降级，但需记录影响。
- Won't：该阶段明确不做，避免隐性扩展范围。

## 1. 项目定位与产品边界

本项目建设一套面向睡眠与康养持续服务的智能随访系统。系统连接康养用户、健康管家、一线医护、上级医师、医疗运营和合作机构，覆盖建档、服务路径、计划任务、问卷答卷、异常关注、主动咨询、处置复核、每日督导、通知和服务评价。

### 1.1 首要价值

1. 康养用户能以低负担方式完成任务、获得服务并追踪处理结果。
2. 一线人员能从统一待办中知道“今天服务谁、为何需要处理、下一步做什么”。
3. 上级医师能通过日报和重点事项完成分层督导，不必逐个翻阅全部用户。
4. 通知、填写、判断、处置、复核、指导和评价均可追溯。
5. 同一用户可进入多个服务路径，共享公共资料，但路径、任务和临床关注事项独立管理。

### 1.2 明确非目标

- 本系统不是急救、急诊或 120 替代渠道。
- 系统不自动作出诊断，不替代医护人员的最终专业判断。
- 阶段一不接入真实呼吸机厂商数据，不依赖正式短信供应商完成演示。
- 阶段一不建设完整 App 或小程序，先采用响应式移动网页。
- 阶段一不拆分微服务；先在基础项目中形成边界清楚的业务模块。
- AI 不得在未批准知识和规则范围外直接向用户输出个体化诊疗结论。

## 2. 成功指标（待甲方确认目标值）

| 指标 | 口径 | 建议试用期目标 |
| --- | --- | --- |
| 任务按时完成率 | 截止时间内已提交任务数 / 已到期任务数 | ≥ 85% |
| 通知可追踪率 | 有发送尝试和最终回执状态的通知 / 全部通知 | 100% |
| 关注事项首次确认时长 | 从生成关注事项到责任人员确认 | P50 ≤ 30 分钟，具体按等级确认 |
| 关注事项闭环率 | 已关闭关注事项 / 到期关注事项 | ≥ 95% |
| 咨询首次响应达标率 | SLA 内首次人工响应 / 全部咨询 | ≥ 90% |
| 日报可复算一致率 | 日报指标与原始记录复算一致 | 100% |
| 敏感越权拦截率 | 越权访问被拒绝并审计 | 100% |
| 移动端关键流程完成率 | 无培训用户完成打开—填写—提交 | ≥ 90% |

这些数值是建议基线，不是已经承诺的合同指标。试用前应结合团队规模、服务包和排班重新确认。

## 3. 分阶段范围基线

### 3.1 阶段定义

| 阶段 | 定位 | 可使用数据 | 退出条件 |
| --- | --- | --- | --- |
| 阶段 0：开发门禁 | 冻结范围、准备环境、消除生成器和权限风险 | 无业务数据 | P0 决策有负责人；环境可启动；开发基线可验证 |
| 阶段 1：展示原型 | 展示 OSA 核心闭环和产品方向 | 纯虚构或明确脱敏的演示数据 | 一条端到端脚本可重复演示；不得声称可真实试用 |
| 阶段 2：小范围试用 | 支持经授权的真实人员、真实流程试用 | 经授权的最小必要真实数据 | OSA、通知、咨询、日报、权限、安全和运维门禁通过 |

## 4. 术语与核心领域对象

| 术语 | 定义 |
| --- | --- |
| 康养用户 | 接受服务的业务主体，不等同于后台员工账号；代码统一命名为 `CareClient`，REST 资源统一为 `/care/clients`，不再混用 patient/customer |
| 公共资料 | 跨 OSA、失眠等路径复用的身份、联系、服务和责任关系资料 |
| 服务路径 | 一类可版本化的持续服务方案，例如 OSA 或失眠 |
| 路径加入记录 | 某用户进入某个服务路径后的独立生命周期记录 |
| 计划模板版本 | 定义 D1–D5 等任务相对时间、角色、问卷和依赖的不可变版本 |
| 计划实例 | 把模板绑定到某用户和明确业务锚点后生成的执行计划 |
| 任务实例 | 计划中的一个具体动作，例如用户填写 D1 问卷或医护复核 |
| 问卷版本 | 已批准并发布后不可原地修改的题目、选项、分支和校验集合 |
| 答卷 | 用户、健康管家或医护对某任务使用的问卷版本提交的结果 |
| 关注规则版本 | 经批准的答案条件、等级、提醒对象和 SLA 集合 |
| 关注事项 | 规则命中后生成的、需要人工确认和处置的业务对象；代码统一命名为 `AttentionCase`，REST 资源统一为 `/care/attention-cases`；不等同于诊断 |
| 业务待办 | 通知失败、逾期未填、关注事项、待复核等需要行动的统一入口 |
| 咨询 | 用户主动提出问题形成的独立工单式对象 |
| 服务互动 | 电话、在线回复、补录、转交、升级、复核等一次具体行动 |
| 通知尝试 | 一次向供应商或模拟通道提交通知的记录，包含受理与回执 |
| 每日汇总版本 | 某统计日按固定口径生成的快照，后续修正形成新版本 |
| AI 建议 | AI 生成、等待人工审核的辅助内容，不是最终回复 |

### 4.1 来源标识

所有答卷、服务记录、处置、设备数据和回复必须标识来源：`用户自填`、`健康管家记录`、`医护填写`、`设备`、`AI 建议`、`系统生成`。代填时还必须记录实际操作人、代填原因和用户确认方式。

## 5. 组织、角色与责任关系

### 5.1 角色

| 角色 | 主要职责 |
| --- | --- |
| 康养用户 | 查看和完成本人任务、发起咨询、查看回复、评价服务 |
| 健康管家 | 日常提醒、非临床跟进、咨询接收、服务记录和升级 |
| 一线医护 | 专业评估、答卷复核、关注事项判断与处置 |
| 上级医师 | 督导下级处理、复核重点事项、指导或直接介入 |
| 医疗运营/项目管理 | 维护服务包、团队、指标口径和运营汇总 |
| 合作机构管理者 | 查看本机构授权范围内的进度和统计，医疗明细另行授权 |
| 内容与规则管理员 | 编制问卷、内容和规则，提交审核；发布需与编制人分离 |
| 医疗审核人 | 审核并批准问卷、规则、阈值和科普内容 |
| 技术支持 | 维护运行和账号配置，默认只看脱敏技术信息 |
| 审计人员 | 在授权范围内查看审计事件，不直接修改医疗业务记录 |

### 5.2 权限由六个维度共同决定

权限不能只按角色判断，应至少考虑：角色、机构、团队、责任关系、数据敏感级别、临时授权。后台员工可以一人多角色，但每次操作应能还原当时生效的角色和数据范围。

## 6. 核心业务流程

### 6.1 建档、授权与责任分配

1. 工作人员录入或导入最小必要信息。
2. 系统按甲方确认的唯一性规则检索潜在重复用户。
3. 对疑似重复记录由授权人员合并或确认新建，禁止静默覆盖。
4. 记录服务告知、数据处理授权、通知授权和 AI 处理授权的版本及证据。
5. 关联合作机构、服务团队、健康管家和责任医护。
6. 后续转交只改变生效中的责任关系，历史关系和历史操作人不变。

### 6.2 启动 OSA 计划与 D1–D5 随访

1. 选择已发布的 OSA 路径和计划模板版本。
2. 明确 D1 业务锚点；建议默认“设备首次有效使用日”，待甲方确认。
3. 预览将生成的任务、开放/截止时间、填写角色和通知时间。
4. 授权人员确认后启动计划，系统以幂等方式生成任务实例。
5. 任务到达开放时间后可填写；未开放任务仅显示计划日期。
6. 用户提交后绑定提交时的问卷和关注规则版本。
7. 通知失败或逾期未填生成相应待办，但除明确暂停/终止外，不自动删除后续任务。
8. 计划可暂停、恢复、取消或重排，所有变化保留原因和操作者。

### 6.3 关注事项闭环

1. 答卷提交后只执行已经批准并绑定的规则版本。
2. 同一答卷命中多条规则时，记录全部命中，事项等级取最高值；是否合并为一个事项由规则组配置。
3. 系统在规定时间内生成唯一关注事项并通知责任人员。
4. 责任人员确认、查看授权答案、记录判断与处置。
5. 需要协作时可转交或升级；SLA 计时不得因转交被清零。
6. 未记录处理结果和关闭理由时不得关闭。
7. 关闭后可由授权人员重开，重开作为新事件，不覆盖原过程。

### 6.4 主动咨询闭环

1. 系统可 24 小时接收在线咨询；是否 24 小时人工响应由排班和 SLA 决定。
2. 咨询记录问题、来源、用户、机构、紧急程度和时间。
3. 系统或值班人员分配给健康管家；专业问题升级一线医护或上级医师。
4. AI 可整理上下文并生成建议，但默认不得直接发送。
5. 服务人员回复、转交、升级或等待用户补充。
6. 记录解决结果后关闭，并按配置发起满意度评价。
7. 页面必须明确提示急症或紧急风险应使用正式急救/就医渠道。

### 6.5 每日汇总与督导

1. 建议默认按 Asia/Shanghai 自然日，于次日凌晨生成前一日汇总。
2. 汇总包含服务人数、任务完成、通知失败、逾期、关注事项、咨询、处置、未结项和需复核项。
3. 统计按业务定义去重，转交和跨日事项不得重复计为多名人员完成。
4. 上级医师可查看授权下级摘要并对重点事项下钻。
5. 指导意见形成独立记录，可要求整改、讨论或直接介入。
6. 原始数据后续修正时生成新的汇总版本，不无痕覆盖旧版。

## 7. 状态机与事件

### 7.1 路径加入记录

`草稿 → 待启动 → 进行中 ↔ 已暂停 → 已完成 / 已终止`

- 只有已发布路径和计划版本可启动。
- 暂停必须记录原因、起止时间和对既有任务的处理策略。
- 已终止不能直接恢复；如重新服务，创建新的加入记录并关联历史。

### 7.2 任务实例

业务状态：`计划中 → 已开放 → 填写中 → 已提交`，另可进入 `已逾期`、`已过期`、`已取消`。

专业复核状态单独维护：`无需复核 / 待复核 → 复核中 → 已复核 / 退回补充`。不得用一个“已完成”同时表达提交和复核。

### 7.3 通知尝试

`待发送 → 已提交供应商 → 已受理 → 已送达 / 失败 / 回执未知`

“入口已打开、开始填写、已提交”是用户交互事件，不是短信状态。每次重试创建新的通知尝试，保留幂等键和供应商回执。

### 7.4 关注事项

`待确认 → 已确认 → 处理中 → 等待用户 / 等待协作 / 等待上级 → 已解决 → 已关闭`

支持 `升级`、`转交`、`退回`、`重开` 事件。状态转换必须记录操作人、角色、机构、理由、前后状态和时间。

### 7.5 咨询

`新建 → 待分配 → 已分配 → 处理中 → 等待用户 / 等待协作 → 已解决 → 已关闭`

关闭后允许重开；重复咨询可关联，但不得直接合并并丢失原始记录。

### 7.6 问卷、规则和计划版本

`草稿 → 审核中 → 已批准 → 已发布 → 已停用`

- 已发布版本不可原地修改。
- 修订生成新版本，历史任务、答卷和事项继续绑定旧版本。
- 已停用版本不可用于新任务，但不影响历史解释。

### 7.7 AI 建议

`已生成 → 待人工审核 → 已采纳 / 修改后采纳 / 已拒绝 → 已发送`

自动自助回复必须走单独的低风险白名单策略，不能复用“建议已生成”状态直接发送。

## 10. 数据、隐私与审计要求

1. 生产、试用、演示和自动化测试环境必须隔离；生产数据不得直接复制到演示环境。
2. 健康和身份信息按甲方制度分类分级，只展示完成职责所需的最小字段。
3. 医疗和服务过程记录不做无痕覆盖或普通硬删除；纠正以修订事件保留前后值。
4. 记录保存、归档、用户纠正、撤回授权、删除或匿名化规则由甲方及合规人员确认。
5. 敏感数据查看、搜索、导出、代填、转交、规则发布、事项关闭/重开、AI 处理和紧急访问必须审计。
6. 审计事件至少含操作者、角色、机构、动作、对象、结果、时间、请求 ID、终端/IP、理由和必要的前后值摘要。
7. 技术支持紧急访问需最小字段、理由、审批、有效期、到期回收和全量审计。
8. 导出敏感明细默认需审批、水印、范围限制和过期控制。
9. 传输使用 TLS；敏感凭证、JWT、数据库密码和外部服务密钥不得写入仓库。
10. 真实试用前完成备份恢复演练、安全事件联系人和处置流程。

## 11. 非功能需求（目标值待确认）

### 11.1 性能与容量

- 常用查询接口 P95 建议 ≤ 1 秒，复杂汇总 P95 建议 ≤ 3 秒。
- 用户提交后生成关注事项建议 ≤ 5 秒。
- 页面首屏和移动端表单应在目标网络环境下可接受；具体以真实设备测试为准。
- 阶段二必须确认机构数、员工数、用户数、每日任务、答卷、通知和峰值并发。
- 列表分页、批量操作和导出必须设上限；长任务采用异步进度和结果通知。

### 11.2 可靠性

- 创建计划、提交答卷、生成事项、发送通知和评价邀请均使用幂等键。
- 外部通道超时不得阻塞业务主事务；失败进入重试或人工待办。
- 建议试用期 RPO ≤ 24 小时、RTO ≤ 4 小时，正式值由甲方确认。
- 定时任务、通知、日报和外部适配器均有日志、指标和告警。

### 11.3 可测试性

- 业务状态转换通过稳定接口测试，不依赖页面私有实现。
- 外部短信、AI、设备和呼叫能力必须有本地/测试适配器。
- 每个阶段建立“需求—用例—证据”追踪矩阵。
- 至少覆盖正常、越权、重复请求、断网、超时、外部失败、转交、重开和跨日场景。

## 12. 阶段验收场景

### 12.1 阶段一展示原型

1. 用一名虚构用户完成建档、责任分配和 OSA 计划启动。
2. 移动端打开 D1 任务，保存草稿并提交已确认或明确标注的演示问卷。
3. 系统只按绑定规则版本判断，命中后生成唯一关注事项。
4. 一线医护确认、记录处置、升级给上级医师并关闭，过程完整可追溯。
5. 后续任务仍按计划显示；模拟通知失败能形成独立待办。
6. 上级医师从日报进入重点事项，查看下级处理摘要并给出指导。
7. 管家、医护、上级和机构管理演示账号看到不同菜单、按钮和数据范围。
8. 全流程可重复演示，刷新或重复点击不会产生重复计划、答卷或事项。

### 12.2 阶段二小范围试用

除阶段一场景外，还必须验收：

- 用户授权、撤回和身份验证；
- 正式通知受理/送达/失败回执及重试；
- 主动咨询、转交、升级、关闭和评价；
- 日报自动生成与原始数据复算；
- 跨机构越权拒绝和敏感访问审计；
- 责任转交、计划暂停/恢复、答卷更正、事项重开；
- 备份恢复、监控告警、应急联系人和上线回滚；
- 无阻断/严重缺陷，所有 P0 用例有可复核证据。

## 16. 已确认工程决策与启用门禁

### 16.1 当前工程决策

1. 三个阶段均属于长期交付范围，按“可独立验收、可持续扩展”的里程碑依次实施。阶段一是正式架构上的第一个闭环，不做用完即弃的一次性 Demo。
2. 接受第 3.2 节作为实现顺序。`Won't` 只表示本阶段不启用，不代表从长期范围删除。主动咨询、满意度、正式通知、失眠/CBT-I、设备自动接入和 AI 按后续阶段继续实现。
3. 当前没有已确认的 2026-08-23 场次、对象、时长和唯一脚本，因此该日期不作为硬截止，也不为赶日期牺牲数据模型、权限或测试。如果后续确认展示场次，另从当前可用功能组成演示脚本。
4. D1 默认锚点采用“设备首次有效使用日”，计划实例保存明确的 `anchorAt`，而不是运行时猜测。D1–D5 的相对开放、截止、执行角色、依赖、补填、暂停和恢复全部进入不可变的计划模板版本；具体医疗任务内容仍由授权人员提供。
5. 开发与自动测试只使用贴近真实流程、字段完整、状态连贯的高质量合成数据。合成数据不冒充真实用户，也不包含开发人员编造的医疗结论；正式内容缺失时，对应业务配置保持“待发布/禁用”。
6. 关注规则引擎只执行“已审核且已发布”的版本。项目不提供默认临床阈值；开发环境可用明确标为测试夹具的合成规则验证引擎，但不得装载为正式业务规则。
7. 组织权限默认采用“机构—团队—人员”层级，并以带有效期的责任关系补充 GVA DataScope：健康管家仅看其负责用户的必要信息，责任/会诊医护看授权医疗明细，上级医师按下级管理范围查看，机构管理员默认不获得医疗明细。身份或责任上下文缺失时 fail-closed。
8. 工程验收由项目负责人使用固定合成账号、可重复脚本和自动化证据完成。真实试用仍需业务、医疗和安全责任人确认各自范围，但不阻塞与该真实能力无关的通用工程。

### 16.2 真实能力启用门禁

以下事项不阻塞通用架构和合成数据开发，只阻塞其对应的真实能力：

1. **真实康养用户数据**：默认关闭；启用前确认身份验证、授权、撤回、最小必要字段和数据保留/删除规则。
2. **正式短信/通知**：默认使用本地测试适配器；启用前确认供应商、资质、模板、验签、回执语义、重试、备用通道和费用边界。
3. **服务 SLA**：默认解释为“系统 24 小时接收”，不承诺人工 24 小时响应；等级、响应时限和升级联系人全部配置化，正式启用前确认。
4. **日报口径**：工程默认时区 `Asia/Shanghai`、自然日统计、未结项跨日结转、历史修正生成新版本；转交归属和经营口径需业务负责人确认后启用正式日报。
5. **运行保障**：本地环境不构成生产可用性承诺；真实试用前确定容量、监控、安全事件责任、备份恢复以及 RPO/RTO，并完成演练。
6. **电话录音/转写**：默认关闭；只有单独授权、用途和保存期限确定后才能启用。
7. **AI**：默认关闭面向用户的自动回复；工作人员影子建议也要在知识来源、人工审核、数据政策和完整谱系明确后启用。
