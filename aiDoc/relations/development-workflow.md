# 开发工作流

## GVA Helper / MCP 约束

如果当前环境可用 GVA Helper 或其他项目专用 MCP 工具，开发前应优先使用它获取项目级建议、约束和示例，再落地具体实现。

## 推荐开发顺序

1. 先分析需求与接口
2. 先设计后端模型和请求结构
3. 再实现 Service 层业务逻辑
4. 再实现 API 层与 Router 层
5. 最后补齐 `initialize/`、插件入口或前端接入
6. 阶段内单个功能完成后只做直接相关的关键验证
7. 整个阶段实现完成后再集中联调并执行全面验收

## 验证分级

- 单功能任务：定向测试、必要编译/静态检查和一条关键流程冒烟；默认不跑全仓回归、完整 Compose 验收或页面点触
- 阶段收口：集中运行全面自动化回归、Swagger/契约、前端构建、Compose/迁移和必要的多角色浏览器验收
- 例外：用户明确要求，或 AI 说明重大风险并获得用户确认后，可以扩大当前任务的验证范围

## 前后端协作顺序

- 后端优先给出稳定接口
- 前端可基于 Mock 或 Swagger 并行开发
- 联调时以后端真实接口契约为准

## 分支策略

- `main`: 主分支 / 生产分支
- `dev-X.Y.Z`: 版本开发分支（如 `dev-2.9.3`），日常开发与 PR 以当前版本开发分支为目标
- 功能分支应合入对应 `dev-X.Y.Z` 后清理；仓库另存有少量历史遗留分支（`v2.4.x`、`i18n` 等），不作为命名参照

## 提交规范

建议使用语义化提交：

- `feat`
- `fix`
- `docs`
- `style`
- `refactor`
- `test`
- `chore`

推荐格式：`type(scope): description`
